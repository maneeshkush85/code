# Original-graph-faithful LTX-2.3 Director Colab pipeline

A single 2343-line Colab script (`LTX23_Director_OriginalGraph_Colab.py`) that parses the source-of-truth ComfyUI workflow JSON (32 nodes / 65 links / 4 groups) and re-executes it through a JSON→parser→node-registry→memory-aware-executor pipeline against the real ComfyUI node classes, keeping LTXDirector node 131 as the master timeline controller. CELLS 1-10 and the Section-41 audit are stdlib-only so `--validate-only` runs with no GPU/torch/ComfyUI; CELLS 11-19 are the GPU execution layer, judgeable only by inspection here. The `--validate-only` smoke test passes (Section-27 all-PASS, Section-41 52/52, honesty block, exit 0) and `py_compile` is clean. The architecture avoids every forbidden V2/V3 pattern (no 5-segment loop, no `linear_blend_overlap`, no per-scene latents, no post-only mux, no silent swallowing), and reference-image absence is a hard error.

Watch for: (1) **confirmed** — the generic widget→function-arg mapping in `_call_comfy_node` fills declared arg names from `widgets_values` positionally and maps link slots by JSON-input-slot index; this is unsafe for the complex custom nodes (LTXDirector 131, rgthree 138, VHS 139) whose widget lists contain UI-only/serialized/control-flow entries that are not positional function arguments, so faithful reproduction on real Colab is not guaranteed by this path. (2) **confirmed** — the "Stage 1 / Stage 2" prose labels are internally consistent with the JSON topology (they are *not* an execution bug), but Stage 1 (the base pass) is the 8-step/denoise-1.0 stage carrying the *lower* guide strength 0.5, which inverts the task-description reading order and will mislead a reviewer skimming the labels. (3) **likely** — LTXDirector 131 has two unlinked input sockets (`optional_latent`, `global_prompt`) that the executor will back-fill from timeline scalar widgets.

**Verdict**: NEEDS_CHANGES

## High-level view

The parse-and-validate half is genuinely data-driven: every Section-27 and Section-41 assertion is read from the parsed graph/timeline rather than hardcoded, so changing a value in the source JSON flips the corresponding check. The timeline is read from node 131's serialized `widgets_values[6]` as required.

The execution half rests on one generic mechanism — `_call_comfy_node` — that maps parsed link slots and widget values onto each node's `INPUT_TYPES` argument names by position. That is correct for the simple builtin nodes (CFGGuider, BasicScheduler, VAELoader) but not reliable for the workflow's most important custom nodes, where `widgets_values` is not a positional argument list. This is the gap between "the graph validates" and "the graph re-executes faithfully," and it is not surfaced in the script's own honesty reporting.

The Stage-1/Stage-2 labeling is a documentation hazard, not a wiring bug: the executor follows the parsed links, so the actual guide/scheduler pairing is whatever the JSON says regardless of the label. But the labels invert the reading order of the task description, so anyone cross-checking labels against the spec will think something is wrong (or miss that it's right).

The Section-25 hard-error registry, the structured Section-35 failure report, and the memory infrastructure are correctly scoped. The checkpoint layer records completed node ids but does not short-circuit re-execution on resume.

### Generic argument mapping is the faithfulness bottleneck

`_call_comfy_node` is the single point through which every node executes, and its argument construction is:

```python
linked_slots = sorted(resolved_inputs.keys())
for slot in linked_slots:
    if slot < len(arg_names):
        kwargs[arg_names[slot]] = resolved_inputs[slot]     # slot index == INPUT_TYPES ordinal
if isinstance(widgets, (list, tuple)):
    wi = 0
    for name in arg_names:
        if name in kwargs: continue
        if wi < len(widgets):
            kwargs[name] = widgets[wi]; wi += 1              # widgets are positional args
```

Two assumptions are baked in, and both hold for the simple builtin nodes but break for the custom nodes that define this workflow.

The first is that a node's JSON `inputs[]` slot index equals its position in `INPUT_TYPES` (`required` then `optional`). That is true only when every earlier `INPUT_TYPES` entry is also a socket. ComfyUI routinely declares widget parameters interleaved with socket parameters, and converting a widget to an input reorders the `inputs[]` array independently of `INPUT_TYPES`. Mapping by name — resolve each link's `to_slot` back to the target node's `inputs[to_slot]["name"]`, then pass that name as the kwarg — removes the assumption entirely.

The second is that `widgets_values` is a positional list of the node's remaining scalar arguments. This is where the workflow's key nodes diverge sharply:

- **LTXDirector 131** `widgets_values` is `[0, 31.5, 31.5, 0, 756, 756, "<serialized timeline JSON>", " | | | | ", "226.0,161.3,...", 0.001, "1.00,...", True, True, True, 24, "seconds", 1280, 720, "maintain aspect ratio", 32, 18, False, ""]`. These are the node's UI widgets (timeline scalars + the serialized track JSON + preview/size controls), not the ordered function arguments the ComfyUI runtime passes. Feeding them positionally onto `INPUT_TYPES` names will not reconstruct the call the ComfyUI graph executor would make. The script parses this timeline correctly for validation, but the *executor* still hands the raw list to the node's function.
- **Power Lora Loader (rgthree) 138** `widgets_values` is a list of dicts (`[{}, {header widget}, {lora1}, ...]`) using rgthree's dynamic-widget protocol. Positionally assigning dicts to arg names cannot work; in practice this raises and the documented `apply_rgthree_lora_fallback` (builtin `LoraLoader` ×4, logged) takes over — so the *primary* rgthree path is effectively dead and the fallback is the real code path on every run. Functionally acceptable (semantics preserved, logged per Section 6) but should be stated plainly rather than presented as a rare fallback.
- **VHS_VideoCombine 139** stores `widgets_values` as a dict; the code keys on arg name (`if name in widgets`), which is the right approach — but it depends on the VHS dict keys exactly matching the node's `INPUT_TYPES` names, and the JSON dict here also carries keys that are not function args.

`RandomNoise 30` (`[0, "fixed"]`) survives only because `arg_names` is just `["noise_seed"]`, so `wi` consumes `0` and stops before `"fixed"` (the `control_after_generate` UI value). That it works here is ordering luck, not a guarantee the mechanism generalizes.

The net effect: the graph *validates* faithfully, but faithful *execution* of the custom nodes is not established by this argument mapper. The most robust fix is to not hand-roll argument mapping at all — build a ComfyUI prompt dict from the parsed graph and let ComfyUI's own executor resolve widgets and inputs, which is the machinery that knows how each node's `widgets_values` maps to its function. If a bespoke executor must stay, nodes 131, 138, and 139 need explicit per-node argument construction rather than the positional fallback.

### Stage labels follow the JSON topology but invert the spec's reading order

Tracing the links confirms the pairing:

```
LTXDirector.video_latent ──► LTXDirectorGuide 133 (guide 0.5) ──► BasicScheduler 33 [linear_quadratic, 8, 1.0]   = BASE   (SamplerCustomAdvanced 31)
LTXVLatentUpsampler 14   ──► LTXDirectorGuide 132 (guide 1.0) ──► BasicScheduler 21 [linear_quadratic, 4, 0.42]  = UPSCALE (SamplerCustomAdvanced 19)
```

The validator's "Stage 1" checks nodes 33/32/28/**133 (strength 0.5)** and "Stage 2" checks 21/20/17/**132 (strength 1.0)** — the labels bind the 8-step base pass to guide 0.5 and the 4-step upscale pass to guide 1.0, exactly what the JSON wires. This is **not** an execution defect: the executor follows the parsed links, so the widget-to-node bindings (guide 0.5 on node 133, 1.0 on node 132, denoise 1.0 on scheduler 33, 0.42 on scheduler 21) are reproduced regardless of the label.

The hazard is cosmetic but real: the task description lists "two guide stages (strengths 1.0 and 0.5)" in that order, so a reviewer mapping "Stage 1 → 1.0" onto the code sees "Stage 1 guide strength = 0.5" and concludes the wiring is wrong when it is right. A one-line comment at each stage block naming the node ids and strength ("base stage = node 133 @ 0.5, feeds 8-step scheduler 33") disambiguates it permanently.

### LTXDirector's unlinked optional sockets

Node 131 declares five input sockets (`model, clip, audio_vae, optional_latent, global_prompt`) but only three are linked. `_resolve_node_inputs` iterates only linked slots, so `optional_latent` (slot 3) and `global_prompt` (slot 4) never enter `resolved_inputs` — they then become eligible for the positional widget back-fill, which can assign a timeline scalar (e.g. widget `0`) to `optional_latent`. Unlinked optional inputs should be left unset so the node applies its own default. Same root cause as the argument-mapping issue; folds into the same fix.

### Checkpoint system records but does not resume

`CheckpointManager` persists `completed_nodes` to `workflow_state.json` and the executor calls `mark_completed` after each node, but `ensure_node_executed` short-circuits only on the in-memory `completed_nodes` set — it never calls `is_completed`/`_try_restore`. Because node outputs are live tensors that aren't serialized, a resumed process cannot skip an expensive node (no cached output to reuse). The mechanism is progress-logging, not crash-recovery of work. Either connect `_try_restore` with an explicit caveat about what can and cannot be resumed, or narrow the docstring's "skip re-executing expensive nodes" claim.

### What holds up

The Section-27 validator and Section-41 audit derive every derivable assertion from the parsed graph/timeline (node types, LoRA names/strengths from node 138, sampler/scheduler/steps/denoise from 20/32/21/33, guide strengths from 132/133 index 2, VHS params from node 139, audio trim from the audio segment), so they cannot silently drift from the source JSON — this resists the "hardcoded green checkmark" failure mode. The Section-25 registry raises a hard error naming the missing node type and its source repo with no silent substitution; the Section-35 failure report captures node id/type/function/input-types/RAM/VRAM and re-raises; reference-image absence is a hard `FileNotFoundError` with the exact expected path and no placeholder generation. The honesty block avoids "guaranteed no crash" language — though, per Issue 6, it should also list the arg-mapping faithfulness risk.
